Hyperwake

Give an agent a real Linux computer, running on your own machine, and talk to it over HTTP.

$ npx hyperwake

The engine starts and prints an address and a token. Hand those to your agent and it can create a computer, run shell commands, read and write files, take screenshots, move the mouse and type, open the desktop in a browser, and delete the whole thing when it is done.

Each computer is a full Omarchy desktop, Arch Linux with Hyprland, running in its own virtual machine. Creating one takes about a second and it becomes usable in under ten.

Real machines

Hardware virtualisation through HVF or KVM, not a container. Root inside, systemd, package manager, the lot.

Fresh every time

Copy-on-write clones of one base image. Nothing you do to one machine is visible to another.

Runs on your hardware

Loopback only by default. No account, no hosted service, nothing leaves the machine.

Requirements

Node 20 or newer, and a hypervisor.

PlatformNeeds
Apple Silicon Macbrew install qemu, Python 3.10+, an SSH client
Linux x86_64qemu-system-x86_64, a usable /dev/kvm, Python 3.10+, SSH

Check before you start. It reports what it found rather than what it assumes, and names anything missing.

npx hyperwake doctor
  platform      darwin/arm64
  python3       yes
  ssh           yes
  docker        yes (prepares images; does not run the guest)
  accelerator   hvf
  qemu          /opt/homebrew/bin/qemu-system-aarch64
  graphics      software (llvmpipe)

  Ready.
On graphics

software (llvmpipe) is normal. The guest gets a DRM render node from virtio-gpu and Hyprland renders on the CPU, which is enough for a working desktop. A QEMU built with virglrenderer reports accelerated (virgl) instead and is faster.

Install

Nothing to install for the engine itself. npx fetches it when you run it.

npx hyperwake          # start
npx hyperwake doctor   # check this host

Building a guest image is a separate step with heavier requirements, covered next. You need the repository for that, because it compiles the guest daemon from Go source.

Build a guest image

Every machine is cloned from one base image, and you build it once.

This step needs more than running machines does

Docker, running. The build compiles the guest daemon and injects it into the root filesystem inside a privileged container.

On Apple Silicon, Try Omarchy installed in /Applications. That is where the base Omarchy filesystem comes from. The script verifies the app's code signature and the checksum of every artifact it takes.

Neither is used again afterwards. Machines run under your own QEMU.

git clone https://github.com/obaid/hyperwake-core
cd hyperwake-core
npm install
python3 bin/native-prepare --output ~/.hyperwake

That writes ~/.hyperwake/image, which is exactly where the engine looks. Pass a different --output only if you also set HYPERWAKE_HOME to match.

It takes several minutes and produces a 16 GB sparse disk. Existing images are never overwritten. To rebuild, move the old directory aside first.

Run the engine

npx hyperwake

It prints an address, a token and the endpoint list, then stays in the foreground. Leave it running and open a second terminal.

export API=http://127.0.0.1:4141/v1
export TOKEN=$(cat ~/.hyperwake/token)

The engine binds to loopback only. Nothing outside your machine can reach it.

Your first computer

1

Create it

curl -s -X POST $API/machines \
  -H "Authorization: Bearer $TOKEN" \
  -H 'content-type: application/json' \
  -d '{"name": "scratch"}'

You get back a machine in booting. Defaults are 4 vCPU, 4 GB of memory and a 40 GB disk.

2

Wait for ready

curl -s $API/machines/$ID -H "Authorization: Bearer $TOKEN"

Usually six to ten seconds. ready means the guest has reported in for this boot and its shell works, not merely that a process started.

3

Run something on it

curl -s -X POST $API/machines/$ID/actions \
  -H "Authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d '{"action": "exec", "command": "grep PRETTY /etc/os-release"}'
{"data": {"exit_code": 0,
          "stdout": "PRETTY_NAME=\"Arch Linux ARM\"\n",
          "stderr": "", "timed_out": false, "truncated": false}}

Actions

Nine verbs, all on POST /v1/machines/{id}/actions, one per request.

ActionBody
exec{"command": "ls ~", "timeout": 30}
read_file{"path": "~/notes.md"}
write_file{"path": "~/notes.md", "content": "hello\n"}
screenshot{}
click{"x": 640, "y": 400, "button": 1}
move{"x": 640, "y": 400}
scroll{"direction": "down", "amount": 3}
type{"text": "hello world"}
key{"key": "super-return"}

exec, read_file and write_file travel over SSH. The rest go over the guest's VNC socket. Either way the connection details come from the runtime, never from the request: a caller says what to do, never where.

Reads return content_base64, because a file is bytes and the trailing newline is the byte a file API most often loses. Files over 1 MiB are refused; use exec to select a smaller portion.

key takes one key or a combination joined with -. In Omarchy, super-return opens a terminal, super-space the launcher, super-k the keybinding list.

The desktop

curl -s -X POST $API/machines/$ID/desktop -H "Authorization: Bearer $TOKEN"
{"data": {"desktop_url": "http://127.0.0.1:4141/desktop#t=...", "expires_in": 60}}

Open that URL in a browser. The desktop is live and interactive, mouse and keyboard included.

The ticket sits in the URL fragment, which browsers never send to a server, so it stays out of access logs and Referer headers. It works once and expires after sixty seconds. Ask for a new URL whenever you need one.

Worth knowing

Changing only the #fragment of a URL does not reload a page, so pasting a fresh ticket over a spent one in the address bar will appear to do nothing. Open it in a new tab instead.

Stop and delete

curl -s -X POST $API/machines/$ID/stop -H "Authorization: Bearer $TOKEN"
curl -s -X DELETE $API/machines/$ID -H "Authorization: Bearer $TOKEN"

DELETE stops the machine first if it is still running, then destroys it and its disk. If it cannot tear the machine down it returns 502 and leaves the machine registered so you can retry. A delete that quietly forgets a running machine would leave you with a virtual machine nobody can name.

API

Every endpoint under /v1 needs Authorization: Bearer <token>. GET /health does not, and GET /desktop carries its own single-use ticket instead.

EndpointDoes
GET /v1endpoint list, and what this host can do
POST /v1/machinescreate a computer and start it
GET /v1/machineslist them
GET /v1/machines/{id}describe one
POST /v1/machines/{id}/startstart a stopped computer
POST /v1/machines/{id}/stopshut it down, {"force": true} cuts power
POST /v1/machines/{id}/actionsdo something inside it
POST /v1/machines/{id}/desktopa browser URL for the screen
DELETE /v1/machines/{id}destroy it and its disk

Errors

StatusMeans
400malformed request, or a bound exceeded
401missing or wrong token
404no such machine
409the machine is not in a state that allows this
502teardown failed; the machine is still registered

Status

status is the engine's conclusion. runtime_status is what QEMU says. They are reported separately because they answer different questions.

StatusMeaning
bootingQEMU is running, the guest has not reported in for this boot
readythe guest has reported in and its shell works
stoppedthe machine is off, its disk intact
unknownthe runtime cannot see the machine

unknown is a real answer, and the engine will give it to you rather than guessing. A runtime that cannot see a machine has not told you the machine stopped. Collapsing those two is how a platform loses track of something it is still running.

The guest is not trusted. Whoever uses a machine is root inside it, so anything it reports is a claim about itself rather than a fact about the platform. The capabilities field is recorded as a claim; readiness is the engine's conclusion.

Troubleshooting

doctor says it is not ready

It names what is missing. On a Mac, brew install qemu. On Linux, install qemu-system-x86_64 and make sure /dev/kvm exists and your user can open it. Inside a cloud VM that usually means the provider has to expose nested virtualisation, which many do not.

Address already in use

Something is already on 4141, usually an engine you forgot about. Find it with lsof -nP -iTCP:4141 -sTCP:LISTEN, or start this one elsewhere with --port=4242.

A machine never reaches ready

tail -40 ~/.hyperwake/runtime/machines/<id>/console.log

HVF does not support GICv2 emulation means the wrong interrupt controller. Set HYPERWAKE_GIC=3 and create the machine again. QEMU's own errors land in runtime.log beside the console log.

Screenshots come back garbled

Partial frames usually mean the capture raced the compositor. Send an input event first, such as {"action": "key", "key": "super"}, then capture again.

Creating or waking fails with a limit

Defaults are two running machines and 8192 MB reserved. Raise them with HYPERWAKE_MAX_RUNNING and HYPERWAKE_MAX_MEMORY_MB, or stop one you are not using. Stopped machines cost disk, not memory.

A machine appears that you did not create

On startup the engine adopts anything the runtime is holding that it does not recognise, naming it adopted-<id>. That means a previous engine was killed hard enough that it never wrote the record. The machine is real; delete it normally.
