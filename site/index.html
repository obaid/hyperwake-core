hyperwake

Throwaway Omarchy computers for your agents.

A real Arch and Hyprland desktop in its own virtual machine, on hardware you already own. One second to make one. Seven to use it. Delete it and make another.

It is a whole computer, not a sandbox

Every machine boots Arch Linux with Hyprland under your platform's own hypervisor. You get root, systemd, pacman, a compositor and a browser. Install what you like, break what you like, then throw it away and make another in a second.

Machines are copy-on-write clones of one image, so a new one costs a second and a few megabytes rather than a copy of the disk. Nothing you do to one is visible to another.

It runs on loopback on your own hardware. No account, no hosted service, nothing leaves the machine.

Start

Two commands on a Mac. One on Linux, if you already have QEMU.

Get a hypervisor

brew install qemu        # macOS, Apple Silicon
sudo pacman -S qemu-full # Linux, and check /dev/kvm exists

Any QEMU works. On macOS it signs itself with the hypervisor entitlement when it is built, so there is no Developer ID and no special runtime to chase.

Run it

npx hyperwake

The first run downloads a guest image, about 1.1 GB, and checks it as the bytes arrive. Then it prints an address and a token and stays in the foreground.

Not sure the machine can do it? npx hyperwake doctor measures rather than guesses, and names anything missing.

Make a computer

export API=http://127.0.0.1:4141/v1
export TOKEN=$(cat ~/.hyperwake/token)

curl -s -X POST $API/machines \
  -H "Authorization: Bearer $TOKEN" \
  -H 'content-type: application/json' \
  -d '{"name": "scratch"}'

Defaults are 4 vCPU, 4 GB of memory and a 40 GB disk. It comes back booting and reaches ready in about seven seconds.

Where everything lives

The engine keeps its token, keys, images and machine disks in ~/.hyperwake. Move it with HYPERWAKE_HOME. It sits outside the package on purpose: npx installs into a cache that gets cleared, and a machine's disk has to outlive the tool that made it.

Open a terminal and run something, from outside the machine

curl -X POST $API/machines/$ID/actions -H "Authorization: Bearer $TOKEN" \
  -d '{"action": "key", "key": "super-return"}'

curl -X POST $API/machines/$ID/actions -H "Authorization: Bearer $TOKEN" \
  -d '{"action": "type", "text": "fastfetch"}'

curl -X POST $API/machines/$ID/actions -H "Authorization: Bearer $TOKEN" \
  -d '{"action": "key", "key": "enter"}'

super-return opens a terminal in Omarchy, super-space the launcher, super-k the list of every keybinding.

Watch it happen

curl -X POST $API/machines/$ID/desktop -H "Authorization: Bearer $TOKEN"

{"data": {"desktop_url": "http://127.0.0.1:4141/desktop#t=...", "expires_in": 60}}

Open it in a browser. The desktop is live, mouse and keyboard included. The ticket rides in the URL fragment, which browsers never send to a server, so it stays out of access logs. One use, sixty seconds.

API

Everything under /v1 takes Authorization: Bearer <token>. GET /v1 lists itself, for an agent to read.

EndpointDoes
POST /v1/machinesmake one and start it
GET /v1/machineslist them
GET /v1/machines/{id}describe one
POST /v1/machines/{id}/startstart a stopped one
POST /v1/machines/{id}/stopshut down, {"force": true} cuts power
POST /v1/machines/{id}/actionsdo something inside it
POST /v1/machines/{id}/desktopa browser URL for the screen
DELETE /v1/machines/{id}destroy it and its disk

Four states, and one of them is honest

StatusMeans
bootingQEMU is running, the guest has not reported in for this boot
readythe guest reported in and its shell works
stoppedoff, disk intact
unknownthe runtime cannot see it

ready is not "the process started". QEMU can be running happily while the guest is still bringing up its network or its compositor. The engine waits for a heartbeat from this boot before it says ready, so the first command you send lands somewhere that can answer it.

unknown is a real answer, and you will get it rather than a guess. A runtime that cannot see a machine has not told you the machine stopped. Collapsing those two is how a platform loses track of something it is still running.

The guest does not get a vote

Whoever uses a machine is root inside it, so anything it reports is a claim about itself, never a fact about the platform. The engine records what a guest says about its own capabilities and then decides readiness itself.

Nothing is forgotten while it still exists

A delete that cannot tear a machine down returns 502 and leaves it registered, with the reason attached. Removing the record and moving on would leave a virtual machine eating memory that nothing can name and nobody can stop.

Trouble

doctor says it is not ready

It names what is missing. Usually brew install qemu, or on Linux a /dev/kvm your user can open. Inside a cloud VM that needs the provider to expose nested virtualisation, and plenty do not.

A machine never reaches ready

tail -40 ~/.hyperwake/runtime/machines/<id>/console.log

HVF does not support GICv2 emulation means the wrong interrupt controller. Set HYPERWAKE_GIC=3 and make the machine again. QEMU's own errors land in runtime.log next to the console log.

Screenshots come back scrambled

The capture raced the compositor. Send an input event first, such as {"action": "key", "key": "super"}, then capture again.

The desktop URL sits on "connecting"

Tickets work once and last sixty seconds. Ask for another. Note that changing only the #fragment of a URL does not reload the page, so pasting a fresh ticket over a spent one in the address bar looks like it does nothing. Open a new tab.

Creating or waking hits a limit

Two machines and 8192 MB by default. Raise HYPERWAKE_MAX_RUNNING and HYPERWAKE_MAX_MEMORY_MB, or stop one you are not using. Stopped machines cost disk, not memory.

A machine you did not make

On start the engine adopts anything the runtime is holding that it does not recognise and calls it adopted-<id>. Something killed a previous engine before it wrote the record. The machine is real. Delete it normally.

Build your own image

The downloaded one suits most people. Build one if you want different packages, or would rather not download anything.

This asks for more than running machines does

It needs Docker running, because it compiles the guest daemon and injects it into the root filesystem in a privileged container. On Apple Silicon it also needs the base Omarchy filesystem, which it takes from a Try Omarchy install in /Applications, verifying that app's signature and every artifact's checksum.

Neither is touched once the image exists.

git clone https://github.com/obaid/hyperwake-core
cd hyperwake-core && npm install
python3 bin/native-prepare --output ~/.hyperwake

That writes ~/.hyperwake/image, which is where the engine looks. A different --output needs a matching HYPERWAKE_HOME. Existing images are never overwritten, so move the old one aside to rebuild.
